# 協作與交付規範

最後更新：2026-04-08

## 文件目的

- 定義本機可用能力、workflow 分層、驗證順序與交付門檻。
- 作為本專案 skills / MCP / capability gate 的唯一 baseline matrix。

## 適用角色

- PM、設計、前端：確認這一輪可依賴哪些工具與技能，以及缺什麼時該如何降級。
- AI agent：作為本機 baseline、workflow layer、驗證與提交規範的唯一詳細來源。
- Reviewer：確認 claim level、evidence、交付與 capability 聲明是否一致。

## 1. 協作流程（最小必做）

1. 先對齊目標、範圍與成功條件。
2. 若任務屬於 reference clone / screenshot-to-code / URL clone，先依 `docs/project/05` 完成 artifact gate。
3. 依 `AGENTS.md` 的規則選用最小必要 skills。
4. 依 `docs/design/01 / 02 / 03` 的 owner 邊界實作。
5. 完成驗證並回報變更摘要、驗證結果、skill 使用情況、claim level 與待決策項。

## 2. Current Codex Baseline

### 2.0 Codex session capability baseline

本專案在 Codex 5.5 類型工作流中，預設把 **Codex 內建 Computer Use** 視為前端除錯、互動檢查與視覺 QA 的第一線工具。

用途：

- 開啟本機頁面、檢查實際 viewport、scroll position、互動狀態與肉眼可見 hierarchy。
- 做 desktop / mobile 的即時視覺判斷，包含 spacing、copy fit、CTA 清晰度、RWD 與截圖證據。
- 在需要「像使用者一樣看頁面」時，優先於 scripted capture 或純 DOM 推論。

分工：

- Computer Use：第一線視覺 truth、互動 truth、人工判斷與截圖 evidence。
- Playwright / capture script：批次路由、重複性 regression、固定 viewport 大量截圖。
- Chrome DevTools / DOM 工具：computed style、layout metrics、console、network 或 hydration 問題診斷。
- Shell / static inspection：搜尋、型別、lint、build、資料來源與程式結構確認。

### 2.0.1 Codex 5.5 operating model

依 OpenAI 2026-04 `Codex for (almost) everything` 與 GPT-5.5 更新，本專案採用以下工作流假設。實際可用能力仍以當前 Windows Codex app session、workspace 權限與已啟用 plugins / apps / MCP 為準。

官方能力轉成本專案工作流：

- Computer Use / in-app browser：用於本機頁面、localhost、RWD、視覺 QA、互動流程、前端微調與遊戲 / app surface 檢查。
- 多 terminal / 多檔案 sidebar / rich preview：用於同一輪內並行檢查 dev server、lint/typecheck、diff、截圖、PDF / spreadsheet / deck / docs 等交付物。
- Plugins / apps / MCP：用於 JIRA、GitLab、GitHub review、Microsoft files、資料庫、部署與第三方工具，但必須先確認當前 session 已提供並已授權。
- Image generation：只在品牌變體、mockup、visual asset 或 image phase 需要時使用；不得取代已確認的 layout truth。
- Automations / memory / thread reuse：用於長任務延續、定期追蹤、跨日 QA 或 PR follow-up；不得取代本輪應完成的明確驗證。
- Summary pane / sources / artifacts：用於追蹤計畫、證據、產出與待辦；回報時仍需用文字列出關鍵結論與驗證結果。

決策原則：

- 需要「像使用者一樣看畫面」時，先用 Computer Use。
- 需要「可重複、大量、可比較」時，再用 Playwright / capture script。
- 需要「精確 CSS / console / network / DOM」時，再用 DevTools / DOM inspection。
- 需要「跨工具或公司系統資料」時，先確認 plugin / app connector 權限，再使用對應能力。
- 需要「跨日或週期性」時，才規劃 automation；單輪可完成的工作不延後成 automation。

### 2.1 Plugins / apps / MCP 精簡原則

Codex 5.5 之後，本專案不再把舊式 MCP 清單當成新機預設 baseline。`chrome-devtools`、`playwright`、`context7`、`fetch`、`memory` 這類能力若由當前 session、Codex app、plugin 或 MCP 提供，視為可用工具；若只存在於歷史 config，應移出預設設定。

原則：

- Codex app 內建 Computer Use / in-app browser 是前端視覺 QA 與互動檢查的第一線。
- Playwright 以專案測試、capture script 或任務臨時工具優先；不預設常駐 MCP。
- DevTools / DOM inspection 只在需要 computed style、console、network 或 hydration 精查時啟用。
- Context / docs 類工具只在需要外部官方文件真相時啟用；不得取代 repo 內 docs 與現有程式碼。
- Memory / automation 類能力只用於跨日、週期性或明確需要延續的任務，不列入一般開發核心。
- Fetch / web 類工具只在需要取得外部頁面或官方來源時啟用，並需在回報中列來源。

目前未列為 repo toolkit 預設：

- `github`
- `figma`
- `chrome-devtools`
- `playwright`
- `context7`
- `fetch`
- `memory`

補充：

- `github` 若由某個 session 或外部 connector 提供，視為額外的 review / trace integration，而不是 repo 預設 baseline。
- repo 內另有版控的 Codex toolkit template，位置在 [`../../tools/codex-toolkit/`](../../tools/codex-toolkit/)；它負責新機還原與重裝，不直接取代本機 live profile。

## 3. Recommended Workflow Layers

### 3.1 Core layer

預設核心層：

- Codex app：Computer Use、in-app browser、多 terminal、多檔案 sidebar、summary / artifacts pane
- Skills：`uiux-pm-collaboration`、`frontend-skill`、`nuxt-ui`、`nuxt`、`vue`、`visual-qa-review`

用途：

- Codex Computer Use：local page navigation、visual QA、responsive inspection、interactive debug、screenshot evidence
- Project scripts / shell：repeatable QA、multi-viewport batch capture、regression evidence、lint、typecheck、format。
- Official docs / web：需要外部文件真相時才查證，並在回報附來源。

### 3.2 Optional layer

可選層：

- Plugins / apps / MCP：`chrome-devtools`、`playwright`、`context7`、`fetch`、`memory`，僅在當前任務需要且 session 可用時啟用
- Skills：`document-writer`、`site-architecture`、`page-cro`、`form-cro`、`copy-editing`、`schema-markup`、`seo-audit`、`analytics-tracking`、`product-marketing-context`、`nuxt-seo`
- Codex features：automations、thread wakeups、image generation、file previews、document / spreadsheet / presentation tools

用途：

- `chrome-devtools` / DOM inspection：computed style、DOM 結構、console / network 與低階 layout 診斷。
- `playwright`：repeatable interaction QA、multi-viewport batch capture、regression evidence。
- `context7`：Nuxt / Nuxt UI / Tailwind / Vue 等外部文件真相。
- `fetch`：HTML / CSS / content 抓取與比對。
- `memory`：跨 session 保存決策、例外規則與進度摘要。
- Optional skills：用於第二層優化、文件整理、SEO、CRO 與策略補強，不預設每輪都啟用
- Automations：用於跨日 follow-up、定期 QA、PR 回訪與長期監控，不用於逃避本輪可完成的驗證。
- File previews / document tools：用於交付文件、簡報、試算表與 PDF QA。

### 3.3 Conditional / session-provided layer

條件層：

- MCP / integrations：`github`、`figma`、Atlassian / JIRA、GitLab、Microsoft Suite、CI、部署、資料庫或其他 session-provided plugins
- Skills：`playwright-interactive`、`imagegen`

規則：

- `github`：當前本機未配置；若 session 或 connector 提供，可用於 PR、diff、review trace。
- `figma`：非 clone Phase 1 必要，僅在 design mapping、moodboard 或設計協作任務啟用。
- 第三方 plugins / apps：僅在使用者要求、任務自然需要，且目前 session 顯示可用時啟用；不得假設所有官方 plugins 在每台 Windows 環境都已授權。
- `playwright-interactive`：只有 session 真正提供互動式 browser 能力、且 Computer Use 不足以完成該互動診斷時才列為 active。
- `imagegen`：只在 fidelity pass 後進入 Phase 2 品牌變體。

## 4. Capability Gate 與 claim labels

### Capability gate

- 前端視覺、RWD、互動或 clone 任務若缺少可渲染頁面的 Computer Use / browser evidence，需標記 `degraded-fidelity`，並說明改用 scripted capture 或 static inspection 的限制。
- 缺少舊式 MCP 不必自動標記 degraded；只有該任務明確需要該能力且無可替代證據時，才標記 `degraded-fidelity` 或對應 claim。
- 缺少 `github` review / diff layer：只有當任務明確需要 PR trace 或 review 協作時，才標記 `degraded-review-trace`
- 缺少 image generation：不阻塞 fidelity pass；若任務已進入品牌變體階段，標記 `degraded-variant`
- `memory`、`figma` 缺失不阻塞 Phase 1 fidelity

### 標準 claim labels

- `same.new-class-ready`
- `degraded-fidelity`
- `degraded-review-trace`
- `degraded-variant`

## 5. Skills 使用原則（Lean core + optional layer）

- 先用 core layer 完成 repo truth、rendered page truth、Nuxt UI 落地與 fidelity pass。
- 前端與公開頁工作預設採「Computer Use first, scripted capture second, DevTools when precise」。
- Optional layer 用於第二層優化，不把所有 skills 視為同等重要。
- Conditional skills / tools 必須先確認當前 session 能力，再決定是否列入 active。
- AI 生圖與品牌圖像變體，不得先於 fidelity artifact 與 layout truth。

## 7. 驗證與 QA

提交前最少檢查：

1. `npm run format:check`
2. `npm run lint`
3. `npm run guard:ui-buttons`
4. `npm run typecheck`

clone / fidelity 任務建議補充：

- `npm run workflow:clone:preflight`
- Codex Computer Use desktop / mobile visual QA
- 必要時補 Playwright batch capture 或 capture script
- 首頁、目標頁與 `/design-system` 抽查

### 7.1 前端視覺 QA 預設流程

前端、公開頁、clone、RWD 或 UI polish 任務，預設依序執行：

1. 用 shell / static inspection 確認 route、component、i18n 與資料來源。
2. 啟動或確認本機 dev server。
3. 用 Codex Computer Use 開啟目標頁，檢查 desktop 與 mobile viewport。
4. 以使用者視角記錄 hierarchy、spacing、copy fit、CTA、互動狀態與 RWD 問題。
5. 若問題需要重複驗證或跨多頁比對，再用 Playwright / capture script 批次補 evidence。
6. 若需要精確 CSS、console、network 或 hydration 診斷，再用 Chrome DevTools / DOM 工具。
7. 回報時明確標註 evidence 來源：Computer Use、Playwright capture、DevTools、static inspection 或測試指令。

原則：

- 視覺判斷以 rendered page 為準，不只依 code 推論。
- 小範圍 UI 修改可用 Computer Use 做快速 QA；全站 regression 才升級到批次 capture。
- 截圖 evidence 應優先保存目標頁 desktop 與 mobile；不要只看單一 viewport。
- Nuxt dev overlay、內部 image/source controls 或 QA toolbar 若影響公開頁判斷，需在 evidence 中說明是否為 dev-only 狀態。

### 7.2 Codex 5.5 SDLC loop

一般 coding / frontend / docs 任務採用以下節奏：

1. **Ground**：用 shell、file reads、docs 與現有執行結果取得 repo truth。
2. **Plan**：用 `uiux-pm-collaboration` 或對應 specialist 鎖定 scope、成功條件與驗證方式。
3. **Implement**：小步修改，避免一次擴張到未確認頁面或未確認 copy。
4. **Inspect**：用 Computer Use / in-app browser 看 rendered result；必要時補 screenshot evidence。
5. **Verify**：跑 `npm run lint`、`npm run typecheck`，按任務補 `guard:ui-buttons`、format、preflight、capture 或 build。
6. **Review**：檢查 diff、未追蹤檔、使用者既有變更與風險。
7. **Report**：回報變更、驗證、skill / tool 使用、風險、假設與後續建議。
8. **Carry forward**：只有跨日、跨工具或週期性任務才建立 automation / reminder / follow-up。

Codex 5.5 工具選用規則：

- 複雜推理、跨檔重構、長任務：使用 GPT-5.5 Thinking / Pro 類型 reasoning；若不可用，使用當前 Codex 預設模型並標註能力限制。
- 快速小修、明確局部調整：不必升級成重 reasoning 或多代理。
- 可並行但不互相阻塞的探索、驗證或文件比對：可用 subagents；不得把下一步立即需要的 blocking work 丟給 subagent。
- 本機 Windows 工作優先使用 Codex app 的同 workspace 能力；CLI / IDE / web / cloud task 只在任務適合時切換。

## 8. Commit / PR 規範

格式：

```text
<type>(<scope>): <subject>
```

規則：

- `type` 使用英文，`subject` 使用中文。
- Breaking change 使用 `type(scope)!: subject`，且 body / footer 含 `BREAKING CHANGE: ...`
- PR title 與 commit 主旨採同格式。
- 合併策略採 `Atomic + Squash`。

## 9. 維運原則與邊界

- `~/.codex/config.toml` 是本機 MCP / feature baseline 的單一來源。
- `tools/codex-toolkit/` 是可共享、可版控、可重建的 baseline template 與 migration toolkit；它不是完整個人 profile dump。
- 啟用新 MCP、plugin、app 或 feature 後，需重啟 Codex 或確認 session 已載入，再宣稱 capability 已生效。
- 整合 Codex app 內建能力後，需把不再必要的 plugins / apps / MCP 從 repo toolkit 預設與個人 config 建議中移出；只保留任務明確需要、目前 session 已授權、且能產生 evidence 的工具。
- `AGENTS.md` 只負責協作 SOP，不再承擔 design system 細則與 clone artifact 細節。
- `docs/design/01 / 02 / 03` 是 design governance、Nuxt UI implementation 與 artifact grammar 真相。
- `docs/project/05` 是 clone artifact、downgrade 與 AI image workflow 真相。
- 若更新 custom skills、task-activated MCP policy、rules 或 repo-local environment，需同步更新 `tools/codex-toolkit/` 對應內容。
- 私人備份一律輸出到 repo 外，例如 `Documents\\codex-migration\\...`，不得提交進 git。
