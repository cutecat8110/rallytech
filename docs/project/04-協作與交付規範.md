# 協作與交付規範

最後更新：2026-05-08

## 文件目的

- 定義本專案的協作流程、能力分層、skills / MCP / plugin policy、驗證順序與交付門檻。
- 作為 RallyTech skills / MCP / capability gate 的唯一詳細 baseline matrix。
- 讓 AI agent、PM、設計、前端與 reviewer 用同一套 claim level 與 evidence 語言溝通。

## 1. 協作流程

每輪任務最小流程：

1. 對齊目標、範圍、成功條件與不可碰觸邊界。
2. 讀取對應 owner 文件與現有程式碼，先取得 repo truth。
3. 依任務選用最小必要 skills；文件任務用 `document-writer`，前端任務必用 `nuxt-ui`。
4. 若任務屬於 reference clone / screenshot-to-code / URL clone，先依 [`./05-Reference-Clone工作流與降級規範.md`](./05-Reference-Clone工作流與降級規範.md) 完成 artifact gate。
5. 依 [`../design/README.md`](../design/README.md) 與 `docs/design/01 / 02 / 03` 的 owner 邊界實作。
6. 完成驗證，回報變更摘要、驗證結果、skill / tool 使用情況、claim level、風險與假設。

## 2. 能力分層

### Core layer

Core layer 是本專案一般開發與前端 QA 的預設能力：

- Codex app：Computer Use、in-app browser、多 terminal、多檔案 sidebar、summary / artifacts pane。
- Shell / project scripts：repo inspection、lint、typecheck、format、capture、preflight。
- Skills：`uiux-pm-collaboration`、`frontend-skill`、`nuxt-ui`、`nuxt`、`vue`、`visual-qa-review`、`document-writer`。

前端與公開頁任務預設採用：

1. Computer Use / in-app browser first：確認 rendered page、viewport、互動狀態與人眼 hierarchy。
2. Playwright / capture script second：處理可重複、批次、多 viewport 或 regression evidence。
3. DevTools / DOM precise only：只在需要 computed style、console、network、hydration 或低階 layout 診斷時使用。

### Specialist layer

Specialist layer 只在任務需要時啟用，不視為每輪必用：

- Clone / reference：`reference-clone-architect`
- Design system：`design-system-architect`
- Copy / content：`b2b-website-copy-strategy`、`copy-editing`
- IA / CRO / forms：`site-architecture`、`page-cro`、`form-cro`
- SEO / schema / tracking：`nuxt-seo`、`seo-audit`、`schema-markup`、`analytics-tracking`
- Asset / image direction：`asset-sourcing-licensing`、`brand-variation-director`
- Testing / tooling：`vite`、`vitest`、`vueuse`、`reka-ui`

### Conditional layer

Conditional layer 只有在目前 session 真正提供、已授權且任務需要時才列為 active：

- MCP / plugins / apps：`github`、`figma`、`chrome-devtools`、`playwright`、`context7`、`fetch`、`memory`、Atlassian / JIRA、GitLab、Microsoft Suite、CI、部署、資料庫等。
- Skills / system capabilities：`playwright-interactive`、`imagegen`、automations、thread wakeups、file preview、documents / spreadsheets / presentations tools。

使用規則：

- 不假設所有 connector 在每台 Windows 環境都已授權。
- 啟用新 MCP、plugin、app 或 feature 後，需重啟 Codex 或確認 session 已載入，再宣稱 capability 已生效。
- 若任務能在本輪完成，不用 automation 逃避必要驗證；automation 只用於跨日、週期性或明確需要延續的任務。

## 3. Skills / MCP Policy

### Skills inventory

目前 repo-tracked non-system custom skills 位於 [`../../tools/codex-toolkit/skills/`](../../tools/codex-toolkit/skills/)。

主要分層：

- Core build / frontend：`uiux-pm-collaboration`、`frontend-skill`、`nuxt-ui`、`nuxt`、`vue`、`visual-qa-review`
- Clone / asset / copy：`reference-clone-architect`、`asset-sourcing-licensing`、`b2b-website-copy-strategy`
- Docs / strategy / SEO / CRO：`document-writer`、`site-architecture`、`page-cro`、`form-cro`、`copy-editing`、`schema-markup`、`seo-audit`、`analytics-tracking`、`product-marketing-context`、`nuxt-seo`
- Tooling / implementation：`vite`、`vitest`、`vueuse`、`reka-ui`
- Conditional / system：`playwright-interactive`、`imagegen`

`.system` skills 由 Codex 安裝提供，不 vendoring 進 repo。

### MCP / plugin 原則

Codex 5.5 類型工作流之後，本專案不再把舊式 MCP 清單當成新機預設 baseline。

以下能力採 task-activated policy：

- `chrome-devtools`
- `playwright`
- `context7`
- `fetch`
- `memory`
- `github`
- `figma`
- 其他 session-provided plugins / apps / MCP

判斷方式：

- 需要外部官方文件真相時，才使用 Context / docs 類工具；不能取代 repo 內 docs 與現有程式碼。
- 需要抓取外部頁面或來源時，才使用 Fetch / web 類工具，並在回報列出來源。
- 需要 PR trace、review 或 issue context 時，才使用 GitHub / GitLab 類 connector。
- 需要設計協作、design mapping 或 moodboard 時，才使用 Figma 類 connector。
- Memory 只用於跨 session 決策、例外規則與進度摘要，不列入一般開發核心。

### Repo-tracked Codex toolkit

Codex toolkit 位於 [`../../tools/codex-toolkit/`](../../tools/codex-toolkit/)。

用途：

- 在新 Windows 電腦上重建 non-system custom skills、rules 與 repo-local Codex environment。
- 保存可共享、可版本控管的 config template 與 migration scripts。
- 不保存完整 live profile，也不保存私人狀態。

版控內容：

- `skills/`：non-system custom skills
- `rules/default.rules`：raw legacy rules artifact
- `templates/config.windows.toml`：Windows config template
- `project/environment.toml`：repo-local environment template
- `scripts/`：安裝、驗證、私人備份腳本

不進版控：

- `auth.json`
- `memories/`
- `sessions/`
- `history.jsonl`
- `session_index.jsonl`
- `.sandbox*`
- `cache`
- `log`
- `vendor_imports`
- `state_*.sqlite*`
- `logs_*.sqlite*`

## 4. 驗證與回報

### Capability gate

- 前端視覺、RWD、互動或 clone 任務若缺少可渲染頁面的 Computer Use / browser evidence，需標記 `degraded-fidelity`，並說明改用 static inspection、scripted capture 或其他 evidence 的限制。
- 缺少舊式 MCP 不必自動標記 degraded；只有任務明確需要該能力且無可替代 evidence 時，才標記 degraded。
- 缺少 GitHub review / diff layer 時，只有任務明確需要 PR trace 或 review 協作，才標記 `degraded-review-trace`。
- 缺少 image generation 不阻塞 fidelity pass；若任務已進入品牌變體階段，才標記 `degraded-variant`。

標準 claim labels：

- `same.new-class-ready`
- `degraded-fidelity`
- `degraded-review-trace`
- `degraded-variant`

### 驗證順序

文件任務至少執行：

```bash
npm run format:check
```

一般前端 / 程式碼任務預設執行：

```bash
npm run lint
npm run guard:ui-buttons
npm run typecheck
```

提交前完整驗證：

```bash
npm run verify
```

clone / fidelity 任務建議補充：

- `npm run workflow:clone:preflight`
- Codex Computer Use desktop / mobile visual QA
- 必要時補 Playwright batch capture 或 capture script
- 首頁、目標頁與 `/design-system` 抽查

### 前端視覺 QA 預設流程

1. 用 shell / static inspection 確認 route、component、i18n 與資料來源。
2. 啟動或確認本機 dev server。
3. 用 Computer Use / in-app browser 開啟目標頁，檢查 desktop 與 mobile viewport。
4. 以使用者視角記錄 hierarchy、spacing、copy fit、CTA、互動狀態與 RWD 問題。
5. 若需要重複驗證或跨多頁比較，再用 Playwright / capture script 補 evidence。
6. 若需要精確 CSS、console、network 或 hydration 診斷，再用 DevTools / DOM 工具。
7. 回報 evidence 來源：Computer Use、Playwright capture、DevTools、static inspection 或測試指令。

### 回報格式

最終回報需包含：

- 摘要：本輪改了什麼。
- 驗證：實際執行的指令與結果；未執行的驗證需說明原因。
- Skill：本輪使用的 skills。
- 風險 / 假設：包含 degraded claim、未驗證項、使用者既有變更與不碰觸邊界。

## 5. Commit / PR 規範

格式：

```text
<type>(<scope>): <subject>
```

規則：

- `type` 使用英文，`subject` 使用中文。
- Breaking change 使用 `type(scope)!: subject`，且 body / footer 含 `BREAKING CHANGE: ...`。
- PR title 與 commit 主旨採同格式。
- 合併策略採 `Atomic + Squash`。
- 禁止使用 `--no-verify` 繞過必要檢查。
